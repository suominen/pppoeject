CVE-2026-68121 (PPPoEject) is a use-after-free in the Linux kernel PPPoE
transmit path (drivers/net/ppp/pppoe.c). pppoe_sendmsg() saves a pointer to
the PPPoE header (ph = pppoe_hdr(skb)) before calling dev_hard_header(),
then reuses it after. A lower device's header callback may reallocate the
skb head with pskb_expand_head() during dev_hard_header(), freeing the old
head — so the later 6-byte header memcpy and the ph->length store write
through the stale pointer into freed slab memory. The trigger blocks a
PPPoE send in copy_from_user() on an attacker-owned FUSE page, then adds
the first non-Ethernet (GRE/IP6GRE) port to an empty team (Fedora) or
bonding (Ubuntu) device, whose delegated header callback expands the head.
The fix reloads pppoe_hdr(skb) through the skb network-header offset after
the device header is built: e9c238f6fe42 (mainline, first in v7.2-rc5) /
bed4caecd723 (stable 7.1.6). Subject: "pppoe: reload header pointer after
dev_hard_header()".

The bug is a LOCAL privilege escalation. Two CVSS vantages, both local:
kernel CNA CVSS 3.1 7.8 HIGH (AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H); Red Hat

github.com/manizada/PPPoEject ships pppoeject_root_repro.py escalating an

Reachability (prose, NOT a verdict axis): reaching the bug needs
  (a) a PPPoE socket (creatable unprivileged; the pppoe module autoloads);
  (b) namespaced CAP_NET_ADMIN to configure the team/bonding + GRE
      topology — an unprivileged local user gets it via `unshare -Urn`,
      which requires unprivileged user namespaces enabled
      (kernel.unprivileged_userns_clone / user.max_user_namespaces > 0);
      a process/container already holding CAP_NET_ADMIN reaches it directly;
  (c) the trigger devices: a team or bonding device, a GRE/IP6GRE lower
      device, and FUSE — all autoload on demand;
  (d) >= 4 CPUs for the exploit's timing-critical workers.
These gate WHO can reach an unpatched kernel; they never downgrade a

Working-tree hygiene: stream a fetch through a pipe — `curl -fsSL <url> |
grep …` — when one pass over the data is enough. If you genuinely need a
scratch file, save it in the worktree under a `.scratch-` prefix (e.g.
`.scratch-advisories.json`), work on it there, and `rm` it before you
commit — never `git add` a scratch file. Write it with `curl -o
.scratch-…` or `… | tee .scratch-… > /dev/null`: a shell redirection into
a file (`> .scratch-…`) is refused by Claude Code even inside the
worktree, and retrying it in another spelling is wasted effort
(`/dev/null` is the one redirection target that passes). Read it back
with an allowlisted reader (`zcat .scratch-x.gz | grep …`,
`jq … .scratch-x.json`).
Don't use /tmp: Bash file reads are confined to the worktree, so a file
there can be written but not read back. The wrapper's `git clean -fd`
sweeps forgotten scratch on the next run, but the only thing you should
leave behind is the edited tracker (and its commit).
